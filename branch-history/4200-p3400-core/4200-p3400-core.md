## Rationale

The syntax and core semantics of P3400, "Specifying Contract Assertion
Properties with Labels" (M11a): with `--[no_]contracts_p3400` (implied by
`--contracts_p3850` unless given, and enabling contracts; an error in C;
passed to g++ by the drivers as `-f[no-]contracts-p3400`), and
`__cpp_contracts_labels` 202609L, as our GCC predefines it.

A precondition, postcondition or `contract_assert` may have an
assertion-control specifier, `<constant-expression>`, before its
attributes.  Its tokens are cached at the specifier
(`cache_contract_label`): a `>` not nested in parentheses ends it, with
template-ids recognized by the coalescing of identifiers.  The label is
scanned with the operand (`scan_cached_contract_label`, so in the complete
class for a member, per instance for a template, after the body for a
deduced return type), in the scope of the predicate
(`scan_contract_label`): it must be a constant expression of a class type
with a nested, accessible type `assertion_control_object`, checked in the
instances when it is template-dependent.  It is `a_contract_specifier::label`, walked and
displayed, copied to file scope with the predicate.  Redeclarations must
have the same label as written, or none on both (`match_contract_specifiers`).
Without the option the specifier is diagnosed and skipped, as GCC does.
After a trailing return type, `pre<` and `post<` end it rather than begin a
template-id (`curr_token_starts_labeled_contract_specifier`, checked in the
type specifiers, the abstract declarator and its pointer operators).

`contract_control` is a keyword.  `using contract_control namespace-opt N;`
is a using-directive (`a_using_decl::is_contract_control`) whose names are
found only by the lookups in an assertion-control specifier or a
`contract_control(constant-expression)` expression
(`in_assertion_control_expression`, cleared in a template instantiation
scope): the three places that apply using-directives skip it otherwise, and
lookups that apply it are not reused as synthesized projection symbols.  An
active using-directive entry records whether its namespace was nominated
only so (`contract_control_only`, also for the namespaces it nominates in
turn), and an ordinary directive for the same namespace, such as a user's
`using namespace std::contracts::labels;` after `<contracts>`'s own
contract_control one, clears it.  A name whose use elsewhere was diagnosed
as undefined is still found there (`do_using_directive_lookup` passes over
the `sk_undefined` symbol).  `contract_control(e)` is a const lvalue for a
constexpr object initialized by the value of `e`, one for each type and
value: the template parameter object for it
(`make_contract_control_object_operand`), as `(value, object)`, a comma
operation marked `is_contract_control_operand` whose first operand is the
value, backed by `e` as written; a non-constant `e` is an error.

The C++-generating back end puts out the label, parenthesized
(`gen_contract_label`), the directive, and a marked operation as
`contract_control(e)` (also where it was folded into a variable's value),
so that g++, given `-fcontracts-p3400`, applies the labels' facets at run
time.  The facets in the front end's own evaluation (constant
evaluation and the C-generating back end's checks, which accept and ignore a
label for now) are 4200's next step (M11b); groups (M11c) after it.

The tests are `tests/tests/contracts/p3400/` and the imports in
`tests/tests/contracts/imported_p3400/`.
