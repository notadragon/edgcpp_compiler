## Rationale

Implement P3595, "Configuration of Contract Evaluation Semantics" -- a
compiler-only proposal with no feature-test macro and no option of its own,
as in the GCC and Clang contracts implementations.  The evaluation semantic
of each contract assertion is chosen by an ordered list of configuration
entries, the first that matches the assertion giving it.  The entries come
from three new options, in command-line order --
`--contract_configuration=JSON`, `--contract_configuration_file=PATH` and
`--contract_group_evaluation_semantic=GROUP:SEMANTIC[,...]` -- followed by
a catch-all for `--contract_evaluation_semantic`.  The JSON form is our
GCC's (`-fcontract-configuration`): an array of objects with an optional
`match` (kind, group, caller, constexpr, namespace, location) and an
`output` (semantic, dynamic).

`contract_config.c` holds it all: a small JSON parser (EDG has none) with
diagnostics at the JSON text's file, line and column; validation of GCC's
schema at option time; and `contract_semantic_for`, the resolution.  The
front end asks only where it evaluates contract assertions itself: constant
evaluation, where each problem is now reported under its own assertion's
semantic (a warning under observe, an error otherwise), and the checks it
generates for the C-generating back end, where each assertion is checked
unless its semantic is ignore.  Through edg_gxx.sh the same options reach
g++, which chooses the semantics of the checks it generates (matching,
dynamic selectors, caller-side checks): `edg_gxx.sh`, edgy's `eccp-gxx` and
`eccp.sh` pass them on.  Only the callee-side question is ever asked here;
a `group` matches no assertion until P3400's labels, the `implicit` kind
none until P3100; `assume` and the `noexcept_*` semantics are replaced by
ignore, enforce and observe, as our GCC does without their papers.  With
the C-generating back end an entry may give only ignore or quick_enforce
outside constant evaluation, and no `dynamic` output (DECISIONS.md E2).
A string field holding a NUL character (`"\u0000"`) is an error, as in GCC
and Clang, never a value cut at the NUL (notadragon_wg21 DECISIONS.md E192
(1)(a), E193 (1)): `required_string` checks every one (`kind`, `group`,
`namespace`, `location`, the `caller` location and namespace, `semantic`,
the `dynamic` name and linkage); the parser keeps each string's length for
that.

Tests: `contracts/config/` (selection by kind, namespace, location and
`constexpr` in constant evaluation; run-time selection under both back
ends; the IL of the C-generating checks; malformed configurations, and a
NUL in each string field, inline and in a file) and 39
GCC and Clang imports in `contracts/imported_p3595/`.

A reviewer should check `config_entry_matches` against GCC's
`config_entry_matches` (contracts-config.cc), and that every option reaches
both the front end and g++.

## Compile gap

The calls of `contract_semantic_for` and `contract_semantic_possible` that
replace the reads of `contract_evaluation_semantic` in `interpret.c`
(`evaluate_contract_assertion`, `evaluate_function_contracts`,
`finish_contract_evaluation`), `statements.c` (`contract_violation_call`)
and `symbol_tbl.c` (`enter_contract_check_routines`) are lines of the
functions 1090-p2900-base-sema-constexpr and 1100-p2900-base-lowering add,
so those commits call what this one defines; so do the per-problem semantic
of `a_contract_problem` and the narrowed `contract_checks_wanted`.  Their
earlier forms are not reproduced (intermediate commits need not build).

The configuration's warning for a `noexcept_*` semantic says that it
requires `--contracts_p4298`, the option 4800-p4298 adds; the text is the
final one, as g++ words it.
