## Rationale

D4405 (P4405), "prove and diagnose evaluation semantics", stage 1, as
scaffolding only (P3-EDG): with `--[no_]contracts_p4405` (implied by
`--contracts_p3850` unless given, and enabling contracts; an error in C;
passed to g++ by the drivers as `-f[no-]contracts-p4405`), and
`__cpp_contracts_prove` 202610L, as our GCC predefines it.  With it comes
`--[no_]contracts_prove_fold`, the folding proving strategy's option, as
GCC's `-fcontracts-prove-fold`: implied by `--contracts_p4405` unless given
(on either side of it), an error in C, mapped from and passed on as
`-f[no-]contracts-prove-fold` by the drivers; with it off, a predicate the
front end makes a constant proves nothing (DECISIONS.md E159 (a)).

Two evaluation semantics, `ces_prove` and `ces_diagnose` (the library's
values 8 and 9, not the paper's 5 and 6), which never evaluate the predicate
and apply only to a contract assertion's analysis evaluation (D4405R0, "The
Analysis Evaluation"): beside its run-time evaluations each assertion has an
analysis evaluation whose semantic, ignore, diagnose or prove, has a lookup of
its own among the configuration entries for it (`"analysis": true`; one with
"caller" is a configuration error, one with `"constexpr": true` never matches,
and its output must be ignore, diagnose or prove with no "dynamic") and
`--contract_analysis_semantic` (as GCC's `-fcontract-analysis-semantic=`,
which the drivers pass to both; without `--contracts_p4405` it is ignore, with
GCC's warning).  `--contract_evaluation_semantic`, a configuration and a group
semantic accept prove and diagnose too: given to a run-time evaluation (but a
dynamic entry's default), they move to the analysis evaluation, which takes
the stronger, and the run-time evaluation becomes ignore
(`resolve_contract_semantics`); without the option each is ignore, with GCC's
warning (once per semantic for a configuration).  Constant evaluation is never
analyzed: an entry with `"constexpr": true` selecting prove or diagnose is a
configuration error, and a prove or diagnose constant evaluation reaches
otherwise is enforce or observe there (`contract_semantic_for`).

Nothing is proven yet, so wherever the front end generates the checks (the
C-generating back end, which accepts both: no exception can escape a check
that is never made) each analysis evaluation with prove is an error and each
with diagnose a warning (`contract_unproven`), "contract assertion cannot be
proven".  A postcondition's and a contract_assert's are diagnosed where the
check would be made, whatever the run-time semantic, once for each assertion
of each definition (`diagnose_unproven_contract`; once per instance of a
template, not again in a P3097 interface wrapper).  A precondition's are made
at each call, in the caller (`diagnose_contract_analyses_in_body`, a walk of
each function body and of each initializer of an object of static storage
duration): a direct call, a constructor call, a destructor call of an
automatic object or a materialized temporary (an elided temporary has none,
and constant destruction and the temporaries of a constant initialization
are not in the IL), and the cleanup of a subobject of a partially constructed
aggregate, whatever the aggregate's storage duration (EDG-150: it was not
analyzed at namespace scope), when it is potentially invoked -- a later
subobject is initialized after it, by an initializer or a default member
initializer, whether or not that can throw; a subobject left to implicit
value-initialization does not count, and the last has nothing after it
(`partial_cleanup_is_potentially_invoked`; E160 (a), as GCC; EDG-153: the
last subobject's cleanup was analyzed too); not a call through a pointer, in an
immediate function, in the constant-evaluated branch of `if consteval`, in
the condition or discarded statement of a constexpr if, nor one folded to a
constant.  A call through the address of a function has no analysis
evaluation, so a precondition can be proven for it only if it is
tautological (D4405R0, "Taking the Address of a Function"), and that is
known to be needed only when the precondition's label allows no run-time
semantic (always_prove, always_diagnose).  So taking the address of a
function there (`&`, the decay, binding a reference, a pointer to member
function; `diagnose_contract_address_taken`) is diagnosed for the first such
precondition analyzed with prove (else with diagnose) whose predicate does
not fold to true (nothing folds with `--no_contracts_prove_fold`): "contract assertion cannot be proven for a call through
the address of" it, or "contract predicate is always false ..." when it
folds to false, an error for prove and a warning for diagnose
(`contract_address_unproven`, `contract_address_always_false`), with a note
for the precondition; a precondition analyzed with prove or diagnose only by
the configuration draws nothing, since this translation unit's configuration
does not determine the calls through the address.  So is destroying an
object of static or thread storage duration, or a temporary extended to it,
through the destructor's address (`note_contract_static_destruction`, from
`record_end_of_lifetime_destruction`), with a note naming the object, and a
static array's element destructor calls are analyzed as well.  Through edg_gxx.sh the front end
gives none of these diagnostics: g++ makes the analysis evaluations and
applies the address-of rule.  Folding and proof are not implemented
(EDG-134).  An erroneous assertion (`contract_assertion_is_erroneous`: its
predicate holds an error, or it is a postcondition that odr-uses a value
parameter that is not const) has had its error and is not analyzed (EDG-145,
found in VF-EDG: it was also reported as unproven).

A P3400 label may allow the two semantics: allowed_semantics is probed for
them too (`a_contract_specifier::label_allowed_proving_semantics`), and so is
the analysis_semantic facet of D4405R0's "P3400R5 Analysis Evaluation
Configuration" (`label_analysis_semantic`: ignore, diagnose or prove, else an
error, as is a facet that is not a constant expression).  With the option the
semantics are chosen by `apply_contract_label_facets_analysis`, as GCC does
(D4405R0, "Adjusting to the Allowed Semantics"): the allowed set splits into
its run-time part R and its analysis part N; the analysis evaluation allows
N, and ignore if R is not empty, and takes the stronger of its semantic and
the label's analysis_semantic; a run-time evaluation allows R, or only
ignore if R is empty; both are adjusted with GCC's best fit, prove and
diagnose at ignore's level, where a walk tries ignore, then diagnose, then
prove before another level (D3595R1, "Adjusting a Semantic to the Allowed
Set"; from prove: prove, diagnose, ignore; from diagnose: diagnose, ignore,
prove); compute_semantic is given the run-time semantic, and a result of
prove or diagnose moves to the analysis evaluation.  So a label allowing only
prove (always_prove) makes every call prove its precondition, and taking its
function's address is an error unless the precondition folds to true.  A value that is no semantic is never
allowed.  Since a label can choose quick_enforce from any configured
semantic, `__builtin_trap` is predeclared for the C-generating checks
whenever labels are enabled (EDG-142, found here: a label allowing only
quick_enforce, in a mode without the builtin, was an error unless the
configuration named quick_enforce).

The tests are `tests/tests/contracts/p4405/` and the imports in
`tests/tests/contracts/imported_p4405/`.  The P3595 imports
`dyn-enforced-shared-block-eh` (GCC's and Clang's, in 2400-p3595's
directory) now use 1000 as their selector value with no arm, as those
compilers' tests do, since 9 is diagnose.

The names of the configuration's semantics (`a_config_semantic`'s
`cs_prove` and `cs_diagnose`, and `semantic_from_name`) sit with
2400-p3595, which names every semantic a configuration can give, as it does
P4298's and P3100's; the diagnostics that list the semantics name the two in
6900-cross-paper-options.

## Compile gap

`apply_contract_label_facets_analysis` names P3100's assume semantic
(`ces_assume`, `contracts_allow_assume_enabled`,
`a_contract_specifier::label_computed_assume_semantic`), which arrives with
6000-p3100-core, and 4210-p3400-facets's check that a label allows some
semantic names this commit's `label_allowed_proving_semantics`.  Two lines of
earlier entries carry this one's changes: 2400-p3595's list of the known keys
of a "match" names "analysis", and 1100-p2900-base-lowering's
`enter_contract_check_routines` predeclares `__builtin_trap` with P3400
labels enabled (`contracts_p3400_enabled`, 4200-p3400-core's; EDG-142).
Intermediate commits of the generated branch need not build (DECISIONS.md
E2, as for GCC and Clang).
